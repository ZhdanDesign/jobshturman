# Локальное приложение HR Shturman: архитектура и план

Редакция 0.1, 9 октября 2026. Основание: ТЗ ред. 0.5 (`01 ТЗ метапроекта поиска работы.docx`), `references/contracts.md` v0.2, `runtime_constraints.md`, `product_update.md`, процедуры этапов 00–25, черновой `scripts/workflow.py`.

Статус всего документа — ПД (предлагаемый дизайн) в терминах ТЗ §2. Решения, которые принимает Ждан, собраны в разделе 8.

## 1. Что это за контур

Приложение запускается на компьютере кандидата. Им пользуются двумя способами:

1. Через свой AI (Claude Desktop / Claude Code, ChatGPT) по MCP. AI интервьюирует, пишет черновики, сопоставляет вакансии с фактами. Хранение, проверки и переходы состояний делает приложение, а не модель.
2. Через минимальный локальный интерфейс в браузере (`http://127.0.0.1:<port>`): анкета-диагностика, заполнение резюме, карточки откликов, статус поиска.

Оба входа вызывают одни и те же сервисы ядра. Поэтому правило «AI не может отметить отклик отправленным без доказательства» действует одинаково из чата и из интерфейса (ТЗ §16: ручной и фоновый запуск используют один orchestrator и одни полномочия).

Это ветка «пользовательская» из ТЗ §6: собственные AI и аккаунты кандидата, состояние в локальном workspace, сохраняется после закрытия чата.

## 2. Слои

```
┌──────────────────────────┐   ┌───────────────────────────┐
│ MCP-сервер (stdio / HTTP)│   │ Локальный UI (127.0.0.1)  │   транспорт: тонкие,
│ tools + resources        │   │ анкета, резюме, карточки  │   без бизнес-правил
└────────────┬─────────────┘   └─────────────┬─────────────┘
             └──────────────┬────────────────┘
                 ┌──────────▼──────────┐
                 │  hrshturman_core    │  домен: объекты, состояния,
                 │  services           │  инварианты, валидация,
                 │  (intake, resume,   │  события, отчёты
                 │   applications,     │
                 │   report)           │
                 └──────────┬──────────┘
          ┌─────────────────┼──────────────────────┐
   ┌──────▼──────┐  ┌───────▼────────┐   ┌─────────▼─────────┐
   │ Store       │  │ VacancyFeed    │   │ (позже) Action    │
   │ SQLite      │  │ адаптер к      │   │ adapter, renderer │
   │ workspace   │  │ collector/     │   │ DOCX/PDF, Telethon│
   └─────────────┘  │ CONTRACT.md    │   └───────────────────┘
                    └────────────────┘
```

- **hrshturman_core** (`../core/`) — чистый Python 3.11+, только стандартная библиотека. Объекты, машины состояний, инварианты из ТЗ §12–14, валидация claim map, журнал событий. Не знает про MCP, HTTP и конкретный сборщик.
- **Store** — SQLite в папке workspace кандидата (`~/HRShturman/workspace/` по умолчанию). Транзакции `BEGIN IMMEDIATE`, версия объекта для оптимистической блокировки, append-only журнал событий. Схема повторяет полезные инварианты `workflow.py` (одна незавершённая попытка отправки на вакансию, фильтр секретов, канонический хеш).
- **VacancyFeed** — порт для вакансий. Своего парсера нет: адаптер читает выход блока 1 по `collector/CONTRACT.md`. До появления контракта ядро принимает вакансии через `import_vacancies` в нейтральном формате (раздел 5).
- **MCP-сервер и UI** — тонкие обёртки над сервисами ядра.

## 4. Как сделать домен общим с веб-контуром (блок 3)

Решение принято вместе с блоком 3: одно доменное ядро `hrshturman_core` в корневой папке `core/`. Его подключают оба контура. Ведёт его локальная ветка, правки веб-контура приходят через координатора.

1. **Ядро не зависит от транспорта и хранилища.** Сервисы получают `Store` через конструктор. Локально это SQLite-файл. Веб-контур делает свою реализацию того же интерфейса на Postgres и добавляет `tenant_id` (ТЗ §8: «В сервисе дополнительно tenant_id»).
2. **Контракты данных — JSON Schema, сгенерированные из ядра.** Если блок 3 выберет TypeScript для фронтенда, он берёт схемы и коды ошибок оттуда, а правила исполняет вызовом backend-сервиса на этом же ядре. Правила переходов (например, «нельзя повторить `send_unknown` без сверки») не дублируются на втором языке.
3. **Идентификаторы и события переносимы.** `candidate_id`, `track_id`, `application_id`, журнал событий и хеши материалов одинаковы в обоих контурах. Это требование миграции local→service из ТЗ §6: перенос без повторной отправки.
4. **Без тяжёлых зависимостей в ядре.** Ядро написано на стандартной библиотеке и задаёт интерфейс хранилища (`Store` / `Tx`). SQLAlchemy, Pydantic и FastAPI из плана веб-контура живут в его адаптерах, а не в ядре. Так локальная установка не тянет серверный стек, а правила остаются в одном месте.

Альтернатива, если веб-контур целиком на TypeScript: общими остаются только JSON Schema и тестовые сценарии (fixtures + ожидаемые переходы), а правила пишутся дважды. Я её не рекомендую: инварианты отправки и полномочий слишком дорого держать синхронными в двух реализациях.

## 5. Граница со сборщиком (блок 1)

Пока `collector/CONTRACT.md` нет, ядро принимает вакансию в нейтральном виде:

```json
{
  "source": "hh",
  "external_id": "123456",
  "url": "https://hh.ru/vacancy/123456",
  "title": "Директор по продажам",
  "company": "ООО Пример",
  "text": "полный текст или null",
  "published_at": "2026-10-08T10:00:00+03:00",
  "collected_at": "2026-10-09T09:00:00+03:00"
}
```

Правила импорта взяты из ТЗ §13 и не зависят от формата сборщика:

- ключ вакансии — `source + external_id`; повторный импорт обновляет снимок, но не сбрасывает состояние карточки (found, draft, deferred и unknown сохраняют свою судьбу);
- нет полного текста — состояние `needs_full_text`, финальная оценка и решение запрещены;
- охват источников (что прочитано, что pending, что упало) приходит из отчёта сборщика и показывается отдельным блоком статуса; «нет вакансий» без охвата не пишем.

Когда появится контракт, добавляется один адаптер `collector_feed.py`, который переводит его формат в этот. Ядро не меняется.

## 6. MCP-поверхность

Реализовано в `hrshturman_local/mcp_server.py`. Каждый инструмент вызывает один метод ядра.

| Tool | Что делает | Этап |
|---|---|---|
| `status_report`, `set_pause` | Состояние, следующий шаг, воронка с ID; пауза | 22, 23 |
| `intake_get`, `intake_save_draft`, `intake_confirm` | Анкета-диагностика и карта запроса | 00 |
| `fact_add`, `fact_set_status`, `fact_list` | Библиотека фактов | 03, 11 |
| `resume_get`, `resume_save`, `resume_approve` | Мастер-резюме с проверкой claim map | 07 |
| `vacancies_import`, `applications_list` | Импорт вакансий и карточки | 14 |
| `application_score`, `application_decide`, `application_prepare`, `application_authorize`, `application_revoke`, `application_record_sent`, `application_record_employer_event` | Карточка отклика | 15–18, 22 |

Ресурсы: `hrshturman://procedure/{stage_id}` (процедура одного этапа 0–25) и `hrshturman://runtime-constraints`. По ТЗ §1 AI получает процедуру текущего этапа, а не весь каталог.

Действия, которые по ТЗ принадлежат кандидату (подтверждение анкеты, фактов и резюме, решение, разрешение, отметка об отправке), в журнале событий записаны с actor `candidate_via_agent`. Так видно, что решение передано через AI, а не нажато в интерфейсе.

Транспорт: `stdio` для Claude Desktop и Claude Code. Это единственный официально поддерживаемый маршрут первого выпуска. HTTP-транспорт (`--http`, streamable HTTP на 127.0.0.1) уже работает как задел для ChatGPT через туннель или удалённый вариант. Ядро для этого менять не нужно.

## 7. План работ

Каждый шаг заканчивается проверкой, которую можно запустить.

| Шаг | Что делаем | Проверка |
|---|---|---|
| 1 | **Доменное ядро** без зависимостей: диагностика, факты, резюме с claim map, карточки откликов с машиной состояний, журнал событий, отчёт о статусе | `cd core && python3 -m unittest discover -s tests`: ДИАГ-02/09, перенос метрики между компаниями блокируется, повторный импорт не сбрасывает состояние, unknown не повторяется, два кандидата изолированы |
| 2 | **MCP-сервер** stdio + HTTP на официальном Python SDK | Настоящий MCP-клиент по stdio проходит маршрут «анкета → факт → резюме → вакансия → отклик → статус»; состояние переживает перезапуск |
| 3 | **Локальный UI**: одна страница без сборки (диагностика, факты и резюме, карточки, статус), JSON API на стандартной библиотеке, 127.0.0.1 | Тесты API (защита Host и Content-Type, конфликт версий); маршрут «анкета → резюме → решение → разрешение → отметка отправки → приглашение» пройден в браузере, в том числе на ширине телефона |
| 4 | **Адаптер сборщика** по `collector/CONTRACT.md` 1.0-draft, API с состоянием (`hrshturman_local/collector_feed.py`) | Тесты на поддельном сборщике по контракту. Живой прогон 10.10.2026 с настоящим сборщиком (HH-поиск и один Telegram-канал): 190 карточек, повтор не создал ни одной новой, частичный охват HH виден в статусе, дочитывание описания перевело карточку в found |
| 5 | **Рендер резюме** DOCX/PDF + проверка извлекаемости текста (`hrshturman_local/render.py`, python-docx + fpdf2, шрифт Arial из macOS) | Рендерится только утверждённая версия; sha256 файлов и результат извлечения записаны на резюме; вёрстка остаётся `not_verified`, пока её не посмотрит человек |
| 6 | **Задачи кандидату, пауза, diagnostic export** | Экспорт не содержит секретов; пауза останавливает новые действия |
| 7 | **Упаковка и установка** на выбранной ОС | Новый участник проходит установку по инструкции |

Шаги 1–5 сделаны. Ядро: `core/hrshturman_core`, 17 тестов. MCP-сервер и интерфейс: `local-app/hrshturman_local`, 6 тестов, из них 2 через настоящий MCP-клиент. Как запускать, см. `README.md`.

## 8. Принятые решения

Решения приняты 9 октября 2026 (координатор по поручению пользователя; пользователь может поменять любое).

1. **Ядро на Python.** Общий пакет `core/hrshturman_core`, ведёт локальная ветка.
2. **AI-среда первого выпуска — только Claude** через локальный MCP (stdio). HTTP-транспорт оставлен как задел для ChatGPT.
3. **Первая ОС — macOS.** Windows не заявляется, пока не пройдёт свою приёмку (ТЗ §18).
4. **Шифрование.** Приложение не шифрует базу само. Файл `workspace.sqlite3` создаётся с правами 0600, а защиту на диске обеспечивает шифрование ОС. На macOS это FileVault: кандидату нужно включить его в «Системные настройки → Конфиденциальность и безопасность → FileVault». Без FileVault база лежит на диске открыто.
5. **Отправка.** В первом выпуске кандидат откликается сам, приложение готовит комплект и ведёт воронку. Автоотправка по HH появится после одного проверенного адаптера (ТЗ MVP-4).
